# Personal OS — V1.1 Product Backlog (canonical)

Post-v1.0.0. Locked reference: tag v1.0.0 at commit bb85c631 on
ManishPratik/Threshold-. Work targets the `develop` branch.

Guiding principle: the next roadmap is driven by observations from real
users. Where an item can only be decided by watching real users, it lives
under **User Feedback** and stays unstarted until an evidence threshold is
met (see Governance). Where the philosophy — *"A promise to yourself,
witnessed."* — and a proposed change conflict, the philosophy wins.

---

## 0. Release-Quality (must ship before v1.1 is called a release)

### RQ-1 — Draft persistence across /welcome/* refresh
- **Why it exists:** `OnboardingSetupProvider` in
  `src/features/onboarding/OnboardingSetup.tsx` holds mission + routine
  drafts in React state only. `WelcomeScreen4` at
  `src/routes/welcome/WelcomeScreen4.tsx` lines 17-20 redirects to
  `/welcome/promise` if `missionDraft` is missing. A tab crash or
  accidental refresh mid-onboarding discards the user's words —
  inconsistent with the philosophy that those words are sacred.
- **Expected user impact:** Applies whenever a tab crashes or the user
  refreshes between `/welcome/promise` and `/welcome/commit`. Consequence:
  total loss of everything typed.
- **Complexity:** M (persist drafts to a scoped IndexedDB key; hydrate on
  provider mount; clear on `commitAll` success).
- **Priority:** P0 — blocks the v1.1.0 tag.

## 1. User Feedback

Items that require observing real users before deciding scope, shape, or
priority. Advancement to implementation is gated by the Governance
evidence threshold below.

### UF-1 — Ritual pacing calibration
- **Why it exists:** The witness ritual timing (0 → 10800 ms sequence with
  5 emotional beats) is documented in the WitnessRitual module stylesheet
  header inside `src/features/onboarding/`. All timings were internally
  chosen; no user data yet shows whether the sequence feels rushed,
  correct, or too long.
- **Expected user impact:** This is the emotional core of onboarding.
  Wrong pacing changes how the ritual lands — from meditative to either
  theatrical or perfunctory. Applies to every first-time user.
- **Complexity:** S (change 6 CSS `animation-delay` values in one file).
- **Priority:** P2 — do not touch until session recordings or interview
  feedback exist.

### UF-2 — Post-activation edit surface for legacy missions
- **Why it exists:** `MissionSummaryCard` at
  `src/features/mission-contract/MissionSummaryCard.tsx` lines 116-124
  hides the "Refusing to lose" row when `mission.refuseToLose` is
  undefined. Legacy users cannot add a value after installing the V2
  build. No prompt, no backfill, per Phase 3 spec.
- **Expected user impact:** Applies only to users installed before the V2
  contract deploy. Frequency unknown; requires signal from the existing
  cohort.
- **Complexity:** M (add an "Add what you're refusing to lose" affordance
  behind Details expand; wire to existing `updateActiveMissionEditable`).
- **Priority:** P3.

### UF-3 — Promise field length reality check
- **Why it exists:** `MISSION_TITLE_MAX = 80` at
  `src/features/mission-contract/missionContractService.ts` line 23. The
  Promise input is a single-line `TextField`. Some users write longer
  sentences (e.g. ≈ 90 chars).
- **Expected user impact:** A truncated Promise breaks the emotional
  weight of the ritual heading and Today card. Applies to the subset of
  users whose natural Promise phrasing exceeds 80 chars — proportion
  unknown.
- **Complexity:** S (raise cap, swap `TextField` for a 2-row `TextArea`).
- **Priority:** P2.

### UF-4 — Should "Why now" be editable post-activation?
- **Why it exists:** `LOCKED_FIELDS` includes `statement` at
  `src/features/mission-contract/missionContractService.ts` lines 52-63.
  "Why now" is intentionally immutable. Users may want to refine the
  sentence as the mission matures.
- **Expected user impact:** Applies to users who want to evolve their
  motivation over the mission's life. Trades philosophical purity ("the
  contract is signed") against acknowledgement of change.
- **Complexity:** S (add `statement` to `EditableMissionFields`; wire
  Details editor).
- **Priority:** P3 — philosophy currently wins.

### UF-5A — Contract completion friction: instrumentation
- **Why it exists:** The V2 contract redesign added two required sections
  (Refusing to lose) and one optional (Honour) beyond the original three
  fields. Observation targets: per-field time-on-task, focus-blur patterns
  (which field is skipped and returned to), abandonment at each
  `/welcome/*` step, correlation between typed length and completion. No
  analytics currently in v1.0.0.
- **Expected user impact:** No direct user-facing change; enables UF-5B
  and the Success Metrics below.
- **Complexity:** M (per-field timing, focus-blur events, per-route
  abandonment counters, ship the events to a local-first analytics sink
  that respects the app's offline-first philosophy).
- **Priority:** P1.

### UF-5B — Contract completion friction: analysis
- **Why it exists:** Splits the observation phase from the implementation
  reaction. Only starts once UF-5A has collected data past the Governance
  evidence threshold.
- **Expected user impact:** Determines whether the five-part contract is
  strengthening commitment or increasing friction. Feeds directly into
  UF-1, UF-3, and any future contract-shape decisions.
- **Complexity:** M-to-L (analysis effort itself is bounded; any
  structural product change it triggers is a separate item).
- **Priority:** P1 — does not start until UF-5A has run long enough to hit
  threshold.

## Success Metrics (how v1.1 will be judged)

Metrics 1-6 are behavioral; metric 7 is qualitative. All require
instrumentation from UF-5A.

1. **Onboarding completion rate** — percentage of users who reach
   `/today` after first landing on `/welcome`. Baseline: none (v1.0.0 has
   no analytics).
2. **Average time to complete the contract** — median seconds from
   `/welcome` to "I promise." press.
3. **Day-2 retention** — percentage of users who open the app on the
   calendar day after their commit.
4. **Day-7 retention** — percentage of users who open the app on day 7
   after their commit.
5. **Contract-fields-completed rate** — percentage of users who fill all
   four required sections (Promise, Why now, Refusing to lose, Duration)
   without abandoning; also tracked as percentage who fill the optional
   Honour section.
6. **Post-activation "Refusing to lose" edit rate** — percentage of users
   who edit `refuseToLose` after the mission is active (signal for whether
   the field evolves with the mission; informs UF-4).
7. **Perceived meaningfulness** — a single optional post-onboarding
   question: *"Did this feel meaningful?"* with a lightweight yes/no or
   1-3 scale, skippable, one-time. Behavioral metrics tell us what users
   did; this tells us why.

## Governance

- v1.0.0 is frozen. Only genuine production defects modify the v1.0.0 tag
  target commit.
- Section 0 (RQ-1) must ship before the `develop` branch can be tagged
  v1.1.0.
- All items above ship on `develop`, then merge to `main` under the
  v1.1.0 tag when the batch is ready.
- **Evidence threshold for User Feedback items:** No User Feedback item
  advances to implementation on anecdotal input alone. Promotion requires
  ONE of: (a) a predefined minimum number of user sessions with UF-5A
  instrumentation showing the pattern, (b) at least three independent
  qualitative interviews surfacing the same issue, OR (c) a documented
  failure mode with reproducible steps. Exact thresholds are tuned per
  item once real usage volume is known, but the principle — "no
  promotion without evidence" — is non-negotiable.
- Explorations (Category 5) never become backlog items without
  user-signal justification clearing the same threshold.
- Any proposed item not on this backlog must be judged against the
  philosophy first, added here second, implemented third.
