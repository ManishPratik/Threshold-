## 0. Engineering

### E-1 — Toolchain Reproducibility Initiative

- **Why it exists.** RELEASE_PLAN W1.3 investigation (recorded in
  `docs/release/release-log-v1.1.0.md`) established that the v1.1.0 build
  is not reproducible: two clean `npm install` runs against the same
  `package.json` can produce different dependency graphs. Root causes
  identified in W1.3:
  - 31 caret (`^`) ranges in `package.json:20-56` cover every declared
    dependency; each permits patch/minor drift as the npm registry moves.
  - `package.json` has no `"packageManager"` field, so each install
    machine uses its own npm version, producing different optional-peer
    install decisions (npm 11 speculatively installs 34 jsdom-family
    optional peers that npm 10 prunes).
  - `netlify.toml:5` sets `command = "npm run build"`, which does not
    force `npm ci`; the build pipeline can re-resolve caret ranges instead
    of installing the committed lockfile verbatim.

  Empirical evidence collected during the CI probe (run
  `31073481712` on branch `chore/lockfile-regen-probe`, artifact
  downloaded to `/tmp/lockfile-probe/`): local npm-11 (2026-08-05) vs CI
  npm-10 (2026-08-06) lockfiles differed on 70 retained-package versions
  and 35 tree-membership entries. Any one of the three causes above is
  sufficient to defeat reproducibility.

- **Scope for v1.2.**
  - `packageManager` pinning: add `"packageManager": "npm@X.Y.Z"` to
    `package.json` matching the version bundled with Netlify's Node
    image.
  - Corepack enablement: local dev one-time `corepack enable` documented;
    Netlify build command prepended with `corepack enable` so the pin
    activates in CI.
  - `npm ci` standardization: `netlify.toml` build command changed to run
    `npm ci` (installs lockfile verbatim, no re-resolve) before
    `npm run build`; local dev guidance in `README.md` explains when to
    use `npm install` vs `npm ci`.
  - Toolchain documentation: `README.md` "Getting started"
    (`README.md:23-29`) plus a new `docs/release/toolchain.md` recording
    the Node + npm pinned versions and rationale.
  - Reproducible release process: RELEASE_CHECKLIST gains a Phase 1
    step "two consecutive clean installs produce byte-identical
    lockfiles" as a hard gate before S2 signs.
  - Preflight validation: a CI job that runs `npm ci`, then
    `rm -rf node_modules && npm install`, then confirms the lockfile is
    unchanged; fails otherwise.

- **Complexity.** M.

- **Priority.** P1 for v1.2 — release-quality invariant. The v1.1.0
  release ships without this fix per Founder ruling 2026-08-06; no
  subsequent release should.

- **Explicitly out of v1.1.0 scope** per Founder ruling 2026-08-06
  (recorded in `docs/release/release-log-v1.1.0.md`). None of the
  proposed changes touch application code, `dependencies`, or
  `devDependencies`; the pin is purely build-infrastructure metadata.

- **What triggers this item to become P0 for v1.2.** If v1.1.0
  post-release watch (RELEASE_PLAN §9 Release Baseline) surfaces any
  build regression traceable to the toolchain non-determinism, this item
  advances to P0 blocker for the v1.2 tag. Otherwise it remains P1 and
  ships at the v1.2 milestone alongside any other planned work.
